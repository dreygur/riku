# rk Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A laptop only binary `rk` (package `riku-client`) built from the shared laptop side code, with `riku` unchanged.

**Architecture:** Move the laptop side modules out of `riku-cli` into two light crates, `riku-args` (command definitions and help) and `riku-remote` (server list, forwarding, dashboard client, client plugins, quickstart). `riku-cli` re-exports them at their old paths so nothing else changes. A new `riku-client` package builds `rk` on top of the two crates only.

**Tech Stack:** Rust workspace, clap 4, existing crates.

**Spec:** `docs/superpowers/specs/2026-10-30-rk-client-design.md`

## Global Constraints

- Project rules in `.claude/CLAUDE.md` bind every task: no `?` in new or touched functions, sibling `_tests.rs`, files about 200 lines, doc comments, no em dashes, no AI attribution in commits (`git commit -F <file> --no-verify`).
- Never use python, perl or any script interpreter to read, edit or search files. Read/Edit/Write tools; grep/sed only for search and mechanical renames.
- `riku` behaviour does not change. Every existing test keeps passing unchanged except for `use` path updates.
- `rk` must not depend on riku-deploy, riku-supervisor, riku-nginx, riku-caddy, riku-plugins, riku-dashboard or reqwest. riku-config and riku-util are allowed.
- Package `riku-client`, binary `rk`, same version as `riku`.
- Gate before every commit: `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test -q` (baseline at e8addf6: 760 passed, 0 failed, 2 ignored).

## Review Focus

1. A moved module silently changing behaviour through a different `crate::` path resolving to another item: expect identical behaviour, guarded by the unchanged existing tests.
2. `rk` run with no server registered: expect an error naming `rk server add`, never a local run.
3. `rk init` or `rk container ...`: expect a refusal telling the user to use `riku`, exit nonzero.
4. Heavy dependencies creeping into `rk` through a transitive path (riku-config or riku-util gaining a heavy dependency later): the cargo tree test fails.
5. Release assets: `rk` tarball and checksum named like the existing `riku` ones so `install.sh` can fetch them.

  src/client_plugins/...   moved
  src/quickstart/...       moved

`riku-cli/src/lib.rs` keeps `pub mod` names by re-exporting: `pub use riku_args::{cli, cmds, placement, help, app_hint};`, `pub use riku_remote::{remote, client_plugins, quickstart, routing};`. riku-supervisor re-exports or calls `riku_util::token::generate_token`.

### Task 3: rk binary

**Files:** create `crates/riku-client/{Cargo.toml,src/main.rs,src/local.rs,src/main_tests.rs,tests/rk_tests.rs,tests/deps.rs}`; root Cargo.toml member.

**Interfaces:**
- Consumes: `riku_args::help::command`, `riku_args::placement::placement_of`, `riku_remote::remote::{route, target, forward, store, server_cmd, dashboard}`, `riku_remote::plugin_cmd::run_plugin`, `riku_remote::quickstart`.
- Produces: binary `rk` (`[[bin]] name = "rk"` in package `riku-client`).

Behaviour (spec "What rk does"):
- Parse with the shared clap tree. Help shows Local commands that rk runs (server, plugin, quickstart, help) and Forwarded commands; Server commands and `container` are hidden from rk's help.
- Forwarded command: resolve target with `-s`, repo remote, default. No server: error `no server selected; add one with rk server add <name> <user@host>, or pass -s <name>` listing registered servers, exit 1. Never runs locally. `--local` given: error that rk has no local mode.
- Client plugin check runs before forwarding, same as riku.
- `dashboard`: only with a resolved server, through the remote dashboard client; without one, the same no server error.
- `init`, `supervisor`, hidden internals, `container`: refuse with `'<cmd>' is not part of rk; run it with riku on the server` (for container: `with the full riku binary`), exit 1.

- [ ] **Step 1:** Write `tests/rk_tests.rs` integration tests running the built `rk` with `XDG_CONFIG_HOME` set on the child only: no server gives the error and exit 1; `rk init` and `rk container export` refuse; `rk server add t riku@nonexistent.invalid` then `rk -s t apps` prints the `[*] t (riku@nonexistent.invalid)` line on stderr and exits nonzero (ssh cannot resolve); `rk -h` lists `server` and `apps` and not `init`. Run, expect FAIL (no binary).
- [ ] **Step 2:** Implement `main.rs` (parse, dispatch) and `local.rs` (server, plugin, quickstart, dashboard arms). Keep main under 120 lines; no `?`.
- [ ] **Step 3:** `tests/deps.rs` forbids the list from Task 2. Gate. Expected all green.
- [ ] **Step 4:** Commit `Add the rk laptop client`.
